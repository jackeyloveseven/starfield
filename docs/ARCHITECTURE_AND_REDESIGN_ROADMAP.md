# Starfield 架构重构与表现重塑路线图（Architecture & Redesign Roadmap）

> 适用范围：`starfield.html`（Web / PWA / Android WebView OTA 入口）与 `android/` 壳工程  
> 基线版本：**v2.0.0.6 (Build 206)**  
> 目标：系统性解决当前版本中 **元素杂乱、核心玩法空洞、卡牌简陋与 Bug 多、安卓 UI 割裂、加载与内存优化极差、未能合理调用手机 GPU** 六大结构性问题，建立可执行、可验收的演进路线。

---

## 一、项目现状与根因诊断（基于 Build 205/206 代码实测）

1. **单体文件极度膨胀（35.96 MB / 35,339 行）**
   - `NarratorClips` 旁白 Base64 占 **15.52 MB**，`SCORES` 8 首内联 MP3 占 **17.55 MB**，仅内联音频就占整包体积的 **92%（33.07 MB）**。
   - 每次只改几十行代码发 OTA，手机仍须整包重下 ~36 MB；Android WebView 冷启动须同步解析 36 MB HTML/JS，推高首屏耗时与 JS 堆内存峰值。
2. **渲染管线处于“CPU 2D Canvas + WebGL 离屏拷贝”的半混合态**
   - 主场景 `#landscape` 仍由 CPU 驱动 Canvas 2D 绘制星空、星云、纸飞机编队、行星环与后处理；3D 星球通过 `LivingPlanetEngine` 在独立离屏 `WebGLRenderer` 中渲染后，逐颗 `drawImage()` 拷贝到每颗星球的 2D 缓存画布，再二次绘制到主画布。
   - 手机端为了保帧率被迫关闭抗锯齿、压缩离屏分辨率（Build 205 仅 `256px`、实际星球直径约 `158px`，Build 206 已提升至 `384px`）、关闭 `postPass` 电影级色调映射与 Bloom，无法发挥现代手机 GPU 的并行与着色器算力。
3. **双 3D 引擎并存与系统割裂**
   - 飞行主场景使用 `LivingPlanetEngine`，星图 / 孵化卡牌使用 `SFPlanetGL`，各自维护一套 `WebGLRenderer`、噪声与地貌构建器。既浪费 WebGL 上下文配额（Android WebView 极易触发 Context Lost），又导致“卡牌里清晰精致，飞起来看反而降级”。
4. **玩法与 UI 历次叠加缺少统一“导演”与设计规范**
   - 空间站、跃迁门、舰队混战、残骸采集、危险区、航行合约、声呐扫描、共振光门同时塞在主循环，视觉和交互互相抢焦点。
   - 多轮迭代在 `starfield.html` 内积累了多套局部样式覆盖，安卓竖屏/横屏下的按钮尺寸、玻璃拟态、字号、弹窗形态与 Safe Area 处理不统一。

## 二、六大核心痛点与系统性解决思路

### 1. 元素杂乱、构图失焦
- **问题根因**：多个 Chunk 各自排重导致跨区块星球在视点堆叠（已在 Build 206 修复）；同时背景星云、近景杂物、空间站、混战光效缺少层级克制。
- **解决思路**：
  - **构图规则化**：引入**单焦点节拍导演（Encounter Pacing Director）**，把旅程划分为“巡航留白 → 主角星/奇观进近 → 短促互动高潮 → 跃迁余韵”四拍，同一时间窗口屏幕只允许 1 个主视觉焦点。
  - **背景克制与裁剪**：退场/降频低辨识度的 2D 杂乱叠加物（如重复混战光点、过密 2D 空间站标识），让行星剪影、大气边缘散射与编队航迹成为绝对主角。

### 2. 核心玩法空洞、重复度高
- **问题根因**：飞行大多时间在“自动巡航 + 偶尔点按钮”，手操反馈偏飘（`wind` 阻尼过软），星核、航行合约、光门与飞船构筑之间缺乏强因果联动。
- **解决思路（三层正反馈闭环）**：
  1. **有手感的微操风险回报**：收紧移动端触控转向响应与指尖跟随阻尼；将**共振光门穿环（连击加速+星尘，Build 206 已打通入账链路）**、**贴近巨星引力弹弓**、**危险区贴边擦弹**做成高回报手动操作窗口。
  2. **行星奇观可交互探索**：靠近特定地貌/文明奇观星球时，不再只是弹出文字 Toast，而是触发可感知的局部探索动作（如轨道扫描解锁地貌切片、引力井采集稀有星核）。
  3. **局外构筑反哺局内飞行**：孵化出的星球卡牌与飞船改装词条直接作用于飞行属性（如转向灵敏度、光门吸附半径、弹弓倍率、特殊奇观发现率），形成“飞得好 → 拿好卡/星核 → 飞得更爽且能进更深星域”的闭环。

### 3. 卡牌系统简陋与各类 Bug
- **问题根因**：`SFPlanetGL` 与飞行引擎双套构建逻辑不一致；卡牌视觉停留在早期弹窗拼装；孵化、命名、背包、提取、奖励之间状态分散，缺少统一状态机与回归校验。
- **解决思路**：
  - **渲染源统一**：抽离单一的星球数据描述（`PlanetSpec`）与共享材质/噪声工厂，确保飞行中所见即卡牌中所藏。
  - **卡牌表现重做**：按稀有度与生态奇观重构卡面层级（动态视差背景 + 实时自转/清漆高光星球 + 清晰的地貌/文明标签 + 一眼可读的词条加成）。
  - **状态机收口**：建立单一 `Inventory & Hatch State Machine`，所有星核增减、孵化、命名、提取均通过明确 Action 落盘并触发 HUD 同步，配合自动化断言脚本拦截静默吞奖励（如 Build 206 修复的 `gate_resonance` 问题）。

### 4. 安卓端 UI 极为不统一
- **问题根因**：不同时期追加的面板（设置、星图、图鉴、商店、合约、停靠提示）各自内联 CSS，边距、圆角、毛玻璃透明度、字体层级和按钮热区不一致；部分面板未适配挖孔屏/底部手势条。
- **解决思路**：
  - **建立单一 Design Token**：在 `:root` 固化一套标准变量（主/次表面背景、边框透明度、字阶、圆角、标准触控热区 `>= 44×44px`、`env(safe-area-inset-*)`）。
  - **状态严格隔离**：明确划分**飞行态（Flight HUD）**与**停靠/菜单态（Modal Sheet）**——飞行态只保留极简透明胶囊与必要战术按钮（零遮挡），所有管理功能统一收进底部/全屏标准 Sheet 模板，禁止半遮挡悬浮窗堆叠。

### 5. 优化极差（加载、内存、OTA 体积）
- **问题根因**：33 MB 音频 Base64 死绑在 `starfield.html`，主循环存在历史遗留对象分配与跨画布频繁同步。
- **解决思路**：
  - **资源外置解耦（最高收益）**：将 `SCORES` 与 `NarratorClips` 拆分为独立 `.mp3` 静态文件，配合 `fetch` 按需流式加载 + `Service Worker` / Cache API 持久化缓存。主 HTML 从 **36 MB 直接降至 ~2–3 MB**，OTA 更新流量减少 **90%+**，冷启动内存与解析耗时成倍下降。
  - **GLB 与纹理按需加载**：仅在需要时异步拉取对应模型，退出面板及时释放非活跃纹理与几何体。

### 6. 没有合理调用手机 GPU
- **问题根因**：目前仍以 CPU Canvas 2D 为主帧缓冲，WebGL 仅作为离屏贴图生成器，每帧还发生 GPU → 2D Canvas 的纹理回传拷贝；手机 GPU 的并行顶点/片元着色能力几乎被闲置，CPU 却长期满载。
- **解决思路（GPU-First 统一管线）**：
  - **消除离屏回传**：把主场景逐步迁入**全屏共享 WebGL2 / Three.js 主渲染管线**，让 3D 星球、3D 行星环（替代 2D `ringHalf`，统一光照与投影）、纸飞机编队与空间门直接绘制在同一主帧缓冲中。
  - **GPU Instancing 批量化**：将星空背景、高速星尘流线、编队尾迹、光门粒子全部改用 `InstancedMesh` / 自定义粒子 Shader，单次或数次 DrawCall 解决上千颗星尘与粒子。
  - **Shader 级全屏后处理**：用低开销的 GPU Shader（半分辨率降采样 Bloom + ACES Filmic 色调映射 + 轻微暗角与胶片颗粒）取代 CPU/2D `ctx.filter`，让手机端也能稳定拥有电影级光泽与通透感。
